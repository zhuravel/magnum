# Rules applied: the phrases scripts/evidence.sh counts per review rule ("Rules applied" in evidence.md).
#
# One rule per line: <rule name> | <pattern>. A later rule is one line. The pattern is an extended regular
# expression in grep -E syntax, case-sensitive; the script matches it with Python's re, so keep to groups, |, [],
# {n,m}, + * ?, escaped \. \( \), and \n for a newline. It is matched against the text of each report directory
# since the run's `since`: the posted review (review.json: the body and the inline comments), the judge's result
# file (*-judge.json: every string in it) and claude-review.md. Blank lines and lines that start with # are
# ignored; a rule's name must not contain " | ".
#
# Where a pattern comes from. The swept set's phrases, (also covers, (missed earlier), (in the fix for, the
# merged-tree "skipped (machine)" line and the platform rule's number or shopify.dev link are the ones the
# skill-economy analysis of master 3e09420 grepped by hand (analysis/11-skill.md of the 2026-10-14 run, "The 13
# rules of 275a217 and the de84b79 sentence"). That analysis quotes no phrase for the count query, the
# operator-only precondition command or the mechanism that cannot be completed (only the one posted case's
# "Across <sha> → <sha>"). Those lines say "skill wording": their patterns come from the rule's own sentence in
# skills/magnum-review/SKILL.md (sections 2 and 4). A review may word such a rule differently, so a low count on
# a "skill wording" line is weaker evidence than a count on a fixed phrase. Add the rule's real phrase once a
# run shows how reviews write it.
